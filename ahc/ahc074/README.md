## 設計

64 窓を 4 窓ずつ 16 組に分け、各組を 8 枚の紙で表す。128 枚を使用し、残り 64 枚は全て穴にする。異なる組の紙は互いの窓を覆わない。紙の移動は各組の連続した 8 枚の範囲内に限定するので、可視性と表示を組ごとに独立して扱える。

4 窓の全 16 通りを必ず表示できる紙の模様を、ローカルで探索した。各候補について 8! = 40,320 通りの重ね順を列挙し、可視な紙の取り出し・差し込みだけを辺とするグラフを作る。目的の表示を持つ状態から逆向き BFS を行うことで、各状態から目的の表示までの最短手数を求める。最短手数が同じ経路の中では、以後の注文を一様分布とした平均手数が小さい到達状態を選ぶ。

実行時に使用する状態は 32 種類に縮まり、32 × 16 = 512 通りの遷移だけを提出ファイルに圧縮して収めた。埋め込んだ表にはテスト入力や注文列を含めていない。方策の全遷移は、紙の可視性・移動後の重ね順・最終表示を別のシミュレーションで検証した。1 組の操作は最大 7 回なので、全体でも最大 112 回であり、制限の 384 回以下になる。

さらに、最初に与えられる 256 商品から各窓のビット列を作り、窓の組み合わせと白黒反転を焼きなましで選ぶ。目的関数は局所方策の平均手数に対する出現頻度の一次近似。探索は最大 12,000 回、前処理の CPU 時間 0.60 秒を上限とする。各組の初期順序も既知の商品頻度から選ぶ。注文は毎回 1 件だけ読み、未来の注文は使用しない。

探索では 3 窓の設計、4 窓の設計、5 窓の設計、比較関係を木で表す設計を比較した。今回試した候補では、4 窓の設計と商品頻度に応じた窓の組み替えを組み合わせたものが良かった。これが最良解である保証はない。

## 検証結果

2026-11-03、公式配布 seed 0–99、CPython 3.13、macOS で検証。スコアは小さいほど良い。

| 方式 | 100 ケースの合計 | 誤注文 |
| --- | ---: | ---: |
| 1 窓ごとに白黒 2 枚、違う窓を 1 手ずつ変更 | 3,277,000 | 0 |
| 4 窓方策＋窓の組み替え 1,200 回（比較段階） | 2,670,830 | 0 |
| 最終版：探索上限拡大＋初期順序の選択 | 2,648,934 | 0 |

最終版は単純解から約 19.2% 削減。各ケースのスコアは 26,214–26,823、1 注文の操作は実測最大 38 回。公式テスタを含む所要時間は 4 並列実行で最大約 0.73 秒だった。AtCoder 本番環境・PyPy の実行時間は未計測であり、この計測値による保証はない。時間制限付きの探索なので、機械や負荷により探索回数とスコアは多少変わる。

公式テスタによる操作の合法性の検証に加え、出力した操作数の合計と公式スコアが等しいことを全ケースで確認した。採点式は `384 * 誤注文数 + 操作数` なので、これにより誤注文ゼロも確認できる。

## 再実行

公式ツールを任意の場所に展開し、その `tools` ディレクトリで `cargo build --release --bins` を実行する。

```sh
python3 ahc/ahc074/benchmark.py /path/to/tools --cases 100 --jobs 4 --json /tmp/ahc074-results.json
python3 ahc/ahc074/benchmark.py /path/to/tools --cases 100 --jobs 4 --baseline
```

提出コード単体の公式テスタによる実行例：

```sh
/path/to/tools/target/release/tester python3 ahc/ahc074_a.py < /path/to/tools/in/0000.txt > /tmp/ahc074-out.txt
```

## 方策表の再生成

`patterns.txt` の 1 行目は探索時の評価値を置く予約欄で、再生成では使用しない。2 行目の整数は各紙の模様の 3 進表現であり、下位桁から順に窓へ割り当てる。桁の 0 が穴、1 が白、2 が黒を表す。

```sh
c++ -O3 -std=c++17 ahc/ahc074/build_policy.cpp -o /tmp/ahc074-build-policy
/tmp/ahc074-build-policy 8 4 ahc/ahc074/patterns.txt > /tmp/ahc074-policy.json
```

生成した JSON は `patterns`、`gradient`、`orders`、`policy` を持つ。提出コードの `DATA` は、その JSON を空白なしで直列化し、zlib level 9 で圧縮して Base85 に変換したもの。模様を変更するときは、対応する方策表も必ず再生成する。
