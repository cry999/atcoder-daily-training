`ahc072_a.submitted.py` / 100 ケース合計: **32,435** / 実行時間 (PyPy) 100 ケース最大 1.35 秒、重いケース最大 1.38 秒

全体方針: 下の「木＋ペア合流」方式と「バス」方式の複数案を解き、良いほうを選ぶ。木＋ペア合流方式では、色を順番に片付ける。合流で得をする 2 色はペアにして同時に処理する。各色の中ではスライムを「木」に集めて塔を作り、塔ごと巣へ運ぶ。ペアの 2 色の根の塔は、帰り道が重なるなら合流させる。

### 色順 DP

- 色 k にかかる手数は「処理済みの色の集合 S」だけで決まる (処理済みの色は帰巣して消え、未処理の色は初期位置で踏み台になる)。
- `dp[S]` = S を処理し終えるまでの最小手数、の bit DP で順番を決める (K ≤ 12 なので間に合う)。
- 各色の運び方は、他の色が全員残っている盤面で決めた経路に固定して見積もる。S に応じて踏み台の有無を反映し、踏み台がなければ跳ぶ距離を短くして数える。

### 乗り先の木

- 巣に近い順に、各スライムを「巣へ直行」か「判断済み (自分より巣に近い) の同じ色で最も近いスライムに乗る」かに決める。
- 乗り先までの手数 < 巣までの手数、かつ乗っても根の塔の高さが `BUILD_H` (= 7) 以下なら乗る。それ以外は巣へ直行 (次に近い候補は探さない)。
- 乗る組は巣から遠い順 (葉の側から) に動かし、組み上がった根の塔を巣へ運ぶ。
- 乗り先へ届かない乗る組 (他の色の高い塔に阻まれた場合) は、乗るのをやめて自分の塔を根にする。

### 踏み台 BFS

- 一団が高さ b のマスに着地すると、次は同じ方向に最大 b+1 マス跳べる、という遷移の BFS で最小手数の経路を決める。
- 着地後に高さ 8 を超えるマスには着地しない。自分の巣からは先へ進まない (乗る組の経路は巣を通らない)。
- 経路は一団を動かす直前の盤面で求め直す (踏み台が先に動いて消えていることがあるため)。

### ペア合流

- ペアの決め方: 色 a と b の組ごとに、根の塔どうしの合流で得をする手数を見積もり (根の塔の位置と匹数は `_plan_walks` から取る。軽くするため踏み台を考えない歩数・合流地点は根のマス・偶奇は無視、1 対 1 に貪欲に組んで合計)、得の合計が最大になる組み方 (最大重みマッチング) を bit DP で求める。得をしない色はペアにしない。
- ペアは DP の順番で先に来る色の位置で、2 色同時に処理する。
- 両方の色の塔を組み上げてから、根の塔どうしを 1 対 1 で合流させる (合計の高さ 8 以下)。
  - 合流地点 m は全マスから選ぶ。下になる塔が先に m へ行き、上になる塔が後から乗る (下の塔の元のマスを m にすれば、下の塔は動かない)。合流した塔で先の巣へ行き、先の色の塊が帰巣したら、残りの塊を後の巣へ運ぶ。
  - 手数 = D(下の塔 → m) + D(上の塔 → m) + G(m → 先の巣、偶奇指定) + D(先の巣 → 後の巣)。他の色の巣は合流地点にしない。
  - 塔全体は 1 手ごとに上下が反転するので、先の巣の色が上になる偶奇の手数で着く経路を、偶奇つき BFS (巣から逆向き) で求める。
  - どちらが上になるか × どちらの巣に先に行くか の 4 通り × 全マス m を比べ、別々に帰るより得をする組を、得の大きい順に選ぶ。実行直前に見積もり直す。
- 合流しない根の塔はそれぞれ巣へ運ぶ。届かない塔は後回しにする。

### 分けて越える (予備)

- 一団のまま届かないとき (高い塔どうしが狭い通路でふさぎ合うなど) は、隣の高い塔 P (高さ g) に `MAX_H - g` 匹以下ずつ分けて乗せ、P を踏み台に先へ跳ばして再合流する (2p 手)。ダイクストラ法で経路を探す。
- ペア処理で高い塔が残るようになってから必要になった (これがないと RE が出る)。

### パラメータを変えた複数案から選ぶ

- 案の候補 `CANDIDATES` を、この順に時間の許す限り (プログラム全体で `TIME_LIMIT` = 1.5 秒まで) 全部解き、スコア (T + 100000 E) が最も良い案を出力する。
  - 候補: tree (`BUILD_H` = 7) → plan (ケース全体の計画型バス) → tree (`BUILD_H` = 6, 5) → bus (`RADIUS` = 0) → tree (`BUILD_H` = 4)。`BUILD_H` は木の塔の高さの上限。
- 次の案が時間内に終わりそうにないとき (それまでの 1 案あたりの最長時間で判断) は打ち切る。案の途中で例外が出たら、その案だけ捨てる。
- 結果 (100 ケースで選ばれた案): tree=7: 35 件 / tree=6: 19 件 / tree=5: 14 件 / tree=4: 9 件 / bus=0: 23 件。

### バス方式 (BusSolver)

- 1 つの塔 (バス) が巡回しながらスライムを拾い、巣を回って降ろす。seed=0 で 43 手の公開動画を参考にした。
  - 拾う: 1 匹だけのマスに着地すると、そのスライムが一番下に入り、以後 k=0 で跳べば一緒に運べる。
  - 降ろす: 巣に着地すると、上から続くその色が帰巣する。同じ色は常に 1 つの塊にしておく。
  - 塔全体は 1 手ごとに反転するので、拾った色がどちらの端に付くか / 巣でどの色が上か は手数の偶奇で決まる。偶奇ごとの最小手数を前向きの偶奇つき BFS で全マス分求めて選ぶ。
- 連鎖方式: バスに乗せるのは今運んでいる色 (cur) と次の色 (next) の 2 色まで。cur は残りを近い順に全部拾ってから巣へ、next は `RADIUS` 手以内のものだけついでに拾う。cur を降ろしたら next が cur になる。バスは毎回、自分の巣から最も遠いスライムから出発する。
- バスに乗っている色の巣だけは通り抜けない (乗っていない色の巣は着地しても何も起きない)。
- 偶奇が合わずどの巣にも降ろせないときは、上の色の塊だけを、残りのバスを踏み台にして巣へ運ぶ。
- 案の候補に ("bus", 1) / ("bus", 3) / ("bus", 0) を追加。`search` は案ごとに例外を捕まえて、失敗した案を捨てる。
- 結果: 選ばれたのは bus=0 (1 色ずつ) が 23 件。next をついでに拾う bus=1 / bus=3 はどのケースでも選ばれず、合計も大きく悪い (99 件で bus=0: 37,182 / bus=1: 46,826 / bus=3: 50,863、tree=7: 35,773)。

### 色ごとに木とバスを使い分ける

- 木＋ペア合流方式の中で、色 (ペアなら 2 色) を処理するたびに、盤面を複製して「木の方式 (`_carry` / `_carry_pair`)」と「その色を 1 色ずつ集めるバス (`_sweep_color`、ペアなら 2 色を順に)」の両方を最後まで試し、手数が少ないほうの盤面を採用する (`_carry_best`)。
- 基本処理に `Board.copy()` を追加。
- 結果: tree=7 の案では、100 ケース中 59 件で計 160 色 (全 740 色) にバスが採用された。重いケースでは 1 案あたりの時間が伸び、20 件中 16 件で 7 案すべては試せなかった (5〜6 案)。

### 高速化

- 合流の見積もりの使い回し: 候補を順位付けするときは、根の塔ごとの BFS・巣からの BFS・偶奇つき BFS の表 (ペアの全根の塔の元のマスを空にした近似) を組の間で使い回す。実際に合流させる直前には正確に見積もり直す。単体ではスコアはほぼ変わらない (+0.02%)。
- 色の順番の使い回し: 色順 DP は最初の木の案 (`BUILD_H` = 7) で 1 回だけ解き、他の木の案でも同じ順番を使う。ペアは根の塔の大きさで変わるので、案ごとに決め直す。
- 経緯: ペアまで使い回すと +0.28% に悪化した (`BUILD_H` = 7 で決めたペアが、上限の低い案に合わない)。

### 色ごとの選択肢を増やす

- `_carry_best` のペアの選択肢に次の 2 つを追加し、全部の中で手数が最も少ないものを採用する。
  - ペアの 2 色をまとめて運ぶバス (`_sweep_colors`): バスが拾う色をペアの 2 色に限った連鎖方式。次の色は距離によらず拾う。
  - ペアを組まずに 1 色ずつ: k, p の順に、それぞれ「木」と「1 色のバス」の良いほうで運ぶ。
- 結果 (tree=7 の案で採用された運び方の延べ回数): 木 727 / 1 色のバス 207 / 1 色ずつ 47 / ペアのバス 12。

### 案の候補の整理

- 一度も最良にならなかった bus=1, bus=3 (ケース全体を 2 色の連鎖バスで解く) を候補から外し、よく最良になる順 (tree=7 → 6 → 5 → bus=0 → tree=4) に並べ替えた。
- 結果: 100 ケースはスコアが全件同じで、最大時間 1.28 → 1.15 秒。重いケースは木の案 1 つが 0.3〜0.4 秒かかるため、まだ 20 件中 14 件で最後の案まで届かない。

### ルートを計画するバス (ペアの 2 色)

- `_carry_best` の「ペアの 2 色をまとめて運ぶバス」を、ルートを計画してから走る形 (`_planned_pair`) に置き換えた。
  - ルートは「拾うスライムの順番」の列で表し、「色 c を降ろす」目印を挟める。列からルートへの読み替え (`_decode`): 満杯なら近いほうの巣で先に降ろす / バスが空なら次のスライムから手数ゼロで新しいバス / 最後は近い巣から降ろす。手数は各地点間の歩数 (踏み台・偶奇は無視) で見積もる。
  - 最初の列は巣から最も遠いスライムから近い順。局所探索 (区間の反転・1 つの移動・目印の追加と削除、改善か同点なら採用) を `PLAN_ITERS` = 2000 回。乱数の種は固定。
  - 実行 (`_run_plan`) は計画の順番で、偶奇つき BFS で 1 区間ずつ。偶奇が合わず拾えないスライムは飛ばし、最後に連鎖バスで片付ける。降ろせないときは切り離し。
- 結果: ペアのバスが採用された回数は 12 → 78 回 (tree=7 の案、延べ)。重いケースでは時間が伸び、5 案すべてを試せたケースは 0 件。

### 1 色のバスも計画型にする

- 計画の部品を色の数によらず使えるように広げた (`_planned(colors, iters)`、バスに乗せる色は 2 色まで。3 色目を拾うときは先に近いほうの巣で 1 色降ろす)。
- `_carry_best` の「1 色のバス」を計画型に置き換えた (ペアの 1 色ずつのバスも同じ)。

### ケース全体の計画型バス ("plan" の案)

- 全色を対象に計画型バスで運ぶ案を、tree=7 の次に追加 (`PLAN_ITERS_ALL` = 5000)。最初の列は、色ごとに遠い順→近い順、色の順番は巣どうしが近い順。
- 結果: 最良になったのは 86 件中 1 件だけ。合計も tree=7 よりかなり悪い (86 件で tree=7: 24,341 / plan=0: 30,892)。seed 0 は 57。この案に時間を取られて、他の案を試せないケースが増えた (1 案しか試せなかったケースが 14 件)。

### 計画の見積もりを偶奇・踏み台を考慮したものにする (抜本策の段階 1)

- 計画型バスの見積もりに使う地点間の手数を、今の盤面のスライムを踏み台にした偶奇つき BFS で「偶数手 / 奇数手」別に求める (`dist2`)。
- `_decode` でバスの中の並び S を追い、拾う (拾った色は一番下、同じ色は 1 つの塊) / 降ろす (降ろす色が一番上) の決まりを満たす偶奇の手数を足す。着けない偶奇しかないときは罰 `PARITY_PENALTY` = 30。
- 背景: 塔の向きといるマスの市松の色の組み合わせ (位相) は、奇数マス跳ぶ限り変わらない。2 色を乗せたバスでは、拾ったスライムの付く端・巣で上に来る色がこの位相で決まる。
- 結果: ケース全体の計画型バス単体 (20 ケース) の実際の手数は 8,492 → 8,054 に減ったが、見積もりは 7,119 で実際より 12% 楽観的 (途中で拾われて踏み台が消える分・バスの匹数による着地制限・巣の通り抜け制限を無視しているため)。100 ケースでは plan=0 は一度も最良にならず (89 件で tree=7: 26,391 / plan=0: 33,126)、全体の改善はわずか。

### ケース全体の計画型バスを焼きなまし法にする (抜本策の段階 2)

- `_planned_sa`: ルートを「バスごとの拾う順番の列」の集まりで表す (各バスは空から始まり空で終わるので、全体の手数は各バスの手数の和)。変更で影響を受けるバスだけを計算し直す。
- 変更: バスの中 (1 つの移動 / 区間の反転 / 降ろす目印の追加・削除)、バスの間 (別のバスへ移す / 入れ替える / 分ける / つなぐ)。温度 2.0 → 0.05 を時間で下げる。最良の解を残して最後に実行。
- 最初の解: 色ごとに遠い順→近い順、`BUS_CAP` 匹ずつバスに分ける。時間は `PLAN_TIME_ALL` = 0.35 秒 (plan の案のみ。色ごとの計画型バスは今までどおり)。
- 結果: plan=0 が単独で最良になったのは 16 件 (前は 0 件)。両方試せた 92 件で tree=7: 27,824 / plan=0: 29,832 と差が縮まった。seed 0 は plan=0 が 56。

- **通り道で同じ色を拾う**: 乗り先の木と同じ操作になるため実装せず。
- **同じ色の中で交互に飛び越える**: 一番下のスライムが 1 マスずつしか進めないため、まとめて歩くより手数が増える。
